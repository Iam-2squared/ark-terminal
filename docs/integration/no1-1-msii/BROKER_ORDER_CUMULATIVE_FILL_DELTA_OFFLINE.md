# Offline cumulative broker order fill progression — no execution ID invention

The MarketSpeed II RSS official 2026-03-30 specification does NOT put broker order IDs in RssExecutionList. RssOrderList does have a unique order number and a cumulative filled quantity. An order-number-targeted filledQty *increase* can be observed in principle without guessing a per-execution ID, provided the order was positively tied to an Ark-originated order and a previous broker observation exists. This may help determine whether at least one SELL fill has happened, but the broker poll does not supply the exact individual fill time, broker execution ID, or legally complete fill-to-cash settlement. Same-timestamp ordering and partial fill cash/slot credits still need provider evidence and reconciliation.

The new pure synthetic_broker_order_delta.mjs checks exact broker order number, symbol, lot, originating signed intent reference, monotonic aggregate fill counter, ownership at origination, source observation clocks and duplicate IDs. It never treats symbol-only personal orders as Ark orders. A SELL intent with zero filled counter does not trigger the buy hold, while a positive SELL fill delta triggers a conservative synthetic buy hold without claiming legal broker-fill provenance. It is explicitly SYNTHETIC_OFFLINE_ONLY; calls with a real mode are rejected. The code does not write, submit, allocate cash, reset Safety or release a slot.

This is an engineering module for future certified broker order linkage, not a second manual gate or a production-ready fill stream. Real source/IDs are not fabricated; integration with a verified RssOrderIDList/OrderList actual book is still unimplemented and requires Windows physical test with Excel RSS order permission OFF. Frozen/manual single-Excel-permission policy remains unchanged.
