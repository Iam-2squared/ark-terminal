9. 4 scoreの時点・percentile契約
================================================================

各candidateは対応する8 rolling-origin blockの凍結モデルで推論。
モデルのtrain終了は当該test blockより前。最新モデル1本の全期間適用は禁止。
特徴はFrozen Entry判断時点までの許可されたcausal情報だけ。
fill時点情報を過去のfirst intentへbackdateしない。

各head hについて、当該blockの凍結済みcompleted-train ID集合へ
同じblockモデルを適用したscore列T_hを固定する。
既存保存列が同一ならreuse。無ければ推論のみで作成、新fitは0。
各headの元train eligibilityの差を台帳に残し、無理に共通化しない。
MRETは元MRET eligible training集合。test側の未来availabilityで変えない。

r_h(s) = (1 + count(x in T_h: x < s)) / (len(T_h)+1)

rP, r2, r3, rMを作る。scoreを加重合成しない。
現在test全体のdecileや将来candidateをpercentile母集団に使わない。
これはtraining-resubstitution基準の相対順位であり、校正済み確率ではない。

今回の唯一の新policy数値境界は1/2。
LOW_h := 2×(1+count(T_h<s)) < len(T_h)+1
HIGH_h := NOT LOW_h

整数で判定し、0.499999等への丸め・後付けepsilonを使わない。
exact1/2はHIGH。missing/nonfiniteはLOWにしない。
1/2は今回固定する設計境界であって、有効性が実証済みの最適閾値ではない。

公式Replayでは対象native候補のscore/causal sourceが全て認証済みであること。
一部が欠けたcandidateを削除して評価しない。
実装上はscore異常なら当該追加介入をABSTAINしV5へ委譲するが、
研究認証ではその欠測を無視せずSOURCE/CONTRACT_BLOCKEDとする。

保存推論と再推論の差はheadの凍結contractで検査。
MRET score許容1e-12を拡張しない。raw score一致だけでなく、
train rank、LOW/HIGH、選択順、actionが独立実装と一致することも要求。

11. D：低評価が一致した、本当の3枠目だけを見送る
================================================================

各Entry batchで、当該armの現在cash/positions/marksのsnapshotを取り、
V5のnative gateとallocationをそのsnapshot上で一度計算する。
これは現在stateに対するV5 proposalであり、保存された未来V5取引表ではない。

native picked list、slot_admission_index、first-pass/water-fill後の
quantity/debitを確定してから、Dを適用する。

介入条件を全て満たすcandidate cだけ：
  1. native gateがADMIT。
  2. native slot_admission_index=3。
  3. native proposal quantity>=100。
  4. batch既存position数＋cより前のnative BUY成功予定数=2。
     （先行candidateがcash/lot失敗し、実際にはSlot1/2になる場合は対象外。）
  5. LOW_P AND LOW_2 AND LOW_3 AND LOW_M。

全てtrueなら、この新規BUYだけを取り消す。
reason=V5_SLOT3_UNANIMOUS_LOW_SHIELD_REJECT。
actual quantity=0。native would-fund quantity/debitは別列へ残す。

pP・Medium・Weak回避・相対monetizationのどれか1軸でもHIGHなら、
DはABSTAINしてV5 proposalをそのまま実行する。
これを「安全と認定」とは呼ばず、V5へ委譲したと記録する。

【同batchの保護】
他のnative candidateのquantity/debitは既に計算した値をそのまま使う。
除外後にbudget・ML比率・water-fillを再計算して他へ資金を配らない。
除外資金はcashに残す。後続candidateの同batch backfillも0。

これにより、そのbatchでのSlot1/2への直接数量変更を防ぐ。
後日のcash/occupancy pathまで同じになる保証ではない。後述で別監査する。

この追加処理は「元V5仕様そのまま」ではなく、明示した新しいBUY veto。
元allocationの数量提案を保持するラッパーとして実装・差分保存する。

13. DRの回収token：未来を見ずに作り、限定して使う
================================================================

DRもDと同じvetoを行う。Dとの差は以下のtoken処理のみ。

Dによるvetoがあり、当該batch実行後にactual open positionsが2つなら、
回収tokenを1つだけ作る。
  token = {session, created_minute, origin_veto_id, held_pair_ids}

tokenは「未来にWinnerが来る保証」ではなく、介入範囲を限定する状態。
同時に保持できるtokenは1つ。重複vetoでtokenを積み増し・期限延長しない。

次の場合にtokenを失効：
  ・actual holding集合がheld_pair_idsと異なった。
  ・新たな3枠目のBUYが成功した（native/救済どちらでも）。
  ・session終了または15:20に到達。

毎分、confirmed SELL処理後・新規Entry処理前に失効確認する。
未保有veto候補の「本来の未来EXIT時刻」でtoken期限を決めない。

救済はcreated_minuteより厳密に後のminuteのみ。同batchでは不可。
拒否した同じEntryを後から買い直さない。新たに到着したFrozen Entry候補のみ。

================================================================
14. DR：V5のSlot3 Reserveだけを、4軸HIGH時に限定解除
================================================================

救済を検討できるのは、次を全て満たすbatchだけ。
  ・tokenが有効で、actual open=2、holding pairが同一。
  ・current minute>created_minute、current minute<15:20。
  ・そのbatchのV5 native picked listが空。

最後の条件は重要。
nativeで買う候補が1つでもある、またはnative admittedがcash/lot失敗した
batchでは救済しない。既存候補を押しのけるreplacement/backfillを作らない。

救済eligible candidate fは全て以下。
  ・V5 Rank-pass、元のB rank、Frozen Entry時点・価格を維持。
  ・same-symbol、source/as-of等の元の現在時点条件を満たす。
  ・native slot_gate_reasonが厳密にSLOT3_RESERVE_FOR_FUTURE_QUALITY。
  ・HIGH_P AND HIGH_2 AND HIGH_3 AND HIGH_M。

C/ML未達、Slot2 Reserve、MAX3満席、cash/lot、cutoff、same-symbolの
拒否を解除する権限は与えない。

同batchに複数eligibleなら、この限定集合だけを以下で一意に選ぶ。
  rP DESC → r3 DESC → rM DESC → r2 DESC → V5 native order。
分数比較は整数交差積で行い、丸め値で排序しない。
1候補だけ。最優先候補がcash/lot不可でも次候補をbackfillしない。

Big Winner軸を先にし、Medium+・monetizationを補助にする。
しかし将来U5/U10の実ラベルを知って選ぶわけではない。
「Bigが来なければ必ずMediumが取れる」とは主張しない。

選んだ1候補を、実際のarm cash/equity/exposure、既存2つのS/A/Bを使い、
V5 allocation.pyのsingleton pickedとして数量計算する。
追加のquantity重み、cap、target、water-fill変更は0。
quantity>=100ならreason=V5_SLOT3_GUARDED_RESERVE_RECOVERYとしてBUYしtoken消費。
quantity<100ならCASH_OR_LOTで終わり、同候補を後時刻に再試行しない。
